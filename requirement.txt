# WooCommerce Product Variation & Checkout Elementor Widget

## 1. Project Overview

Create a lightweight custom WordPress/WooCommerce plugin using **Pure PHP + JavaScript/CSS where necessary**.

Do NOT use React.

Do NOT build a separate React dashboard.

Do NOT create a separate custom checkout system.

The plugin's primary purpose is to provide a single custom **Elementor Widget** that can be placed anywhere inside an Elementor-designed page.

The widget will:

1. Select a WooCommerce product.
2. Detect whether the product is Simple or Variable.
3. If the product is Variable, display its attributes/variations.
4. Allow the Elementor editor to control how each attribute is displayed.
5. Allow the product title, image, price, quantity and other elements to be shown/hidden.
6. Provide complete Elementor-native styling controls.
7. Support responsive styling.
8. Display the native WooCommerce checkout below the product/variation section.
9. Allow the customer to complete the order directly from the same page.
10. Submit the order through WooCommerce's native checkout system.
11. Redirect the customer to the normal WooCommerce Thank You / Order Received page.

# 3. Main Elementor Widget

Create one Elementor widget.

Widget name:

**Product Variation & Checkout**

The widget should be available inside Elementor.

The user should be able to drag the widget onto any Elementor page.

Example:

```text
Elementor Page
│
├── Hero Section
├── Product Information
├── Marketing Content
│
└── Product Variation & Checkout Widget
       │
       ├── Product Section
       ├── Variation Selection
       ├── Price
       ├── Quantity
       └── WooCommerce Checkout
```

The plugin should not control or build the rest of the page.

---

# 4. Product Selection

The widget must provide:

### Current Product

A toggle:

**Use Current Product**

Default:

**ON**

When enabled, the widget automatically detects the current WooCommerce product.

This is especially important when the widget is used on:

* WooCommerce Single Product templates
* Elementor Single Product pages
* Dynamic product pages

---

# 5. Manual Product Selection

When:

**Use Current Product = OFF**

show a product search/select field.

Example:

```text
Use Current Product
[ ON/OFF ]

Select Product
[ Search product by name... ]
```

The user should be able to:

1. Type a product name.
2. Search WooCommerce products.
3. See matching products.
4. Select one product.

Do NOT require manually entering a Product ID.

The selected product should be saved inside the Elementor widget settings.

The product search should be efficient and should not unnecessarily load the entire product catalog.

---

# 6. Supported Product Types

The widget must support:

### Simple Product

If the selected product is a simple product:

* Product title
* Product image
* Price
* Quantity
* WooCommerce checkout

should be displayed according to the Elementor settings.

No variation selector is required.

### Variable Product

If the selected product is a variable product:

Automatically detect its variation attributes.

Example:

```text
Color
Size
```

or:

```text
Size
Color
Material
```

Only attributes that actually exist on the selected product should be displayed.

---

# 7. Dynamic Attribute Detection

When a Variable Product is selected in Elementor, the widget editor should detect its available attributes.

Example:

```text
Variation Attributes

Color       [ Type: Image ▼ ]
Size        [ Type: Button ▼ ]
```

If the selected product has:

```text
Color
Size
Material
```

then Elementor should automatically show:

```text
Color
Size
Material
```

The developer must not hard-code attribute names such as Color or Size.

Any WooCommerce variation attribute should be supported.

---

# 8. Attribute Display Type

For every detected variation attribute, provide a type selector.

Available types:

### Image

Display the options as image-based selectors.

Example:

```text
Color

[ Black Image ] [ White Image ] [ Red Image ]
```

### Button

Display the options as buttons/text selectors.

Example:

```text
Size

[ S ] [ M ] [ L ] [ XL ]
```

The user must be able to choose the display type independently for every attribute.

Example:

```text
Color  → Image

Size   → Button

Material → Button
```

---

# 9. Image Attribute Logic

If an attribute is configured as:

**Image**

the widget should attempt to display the relevant variation/product images.

Example:

```text
Color

[ Black Image ]
[ White Image ]
[ Red Image ]
```

If a suitable image is available, display it.

If no image is available but the attribute has a usable color/value, provide a sensible fallback instead of displaying a broken image.

The system must never display broken image elements.

---

# 10. Button Attribute Logic

If an attribute is configured as:

**Button**

display the attribute value as a selectable button.

Example:

```text
Size

[ S ] [ M ] [ L ] [ XL ]
```

The selected option must have a clear active state.

Invalid/unavailable combinations should be disabled where possible.

# 20. Order Button

7. Create a normal WooCommerce order.
8. Redirect to the WooCommerce Thank You / Order Received page.

# 32. Editor vs Frontend Product Context

The widget must handle both:

### Elementor Editor

When editing the widget:

* Detect current product where possible.
* Allow manual product selection.
* Load selected product data for preview.
* Render representative variation/checkout UI.

### Frontend

Use the actual current/selected WooCommerce product and real customer/session data.

Do not expose sensitive customer/order information in the editor preview.

# 33. Performance

The plugin must remain lightweight.

Do not use React.

Do not load unnecessary libraries.

Only load plugin CSS/JS when the widget is actually used.

Avoid unnecessary AJAX requests.

Avoid unnecessary WooCommerce checkout initialization.

Do not duplicate WooCommerce checkout functionality.

The checkout should render as quickly as possible.

---

# 34. Checkout Loading Issue

The checkout must not remain stuck in a loading state after the page loads.

Avoid unnecessary loading screens such as:

```text
Loading checkout...
```

for an extended period.

Use WooCommerce's existing checkout scripts and initialization process correctly.

Do not initialize the checkout multiple times.

Do not trigger unnecessary checkout update requests during initial page load.

The customer should see the checkout as quickly as possible.

---

# 35. Security

* Validation

* WooCommerce server-side validation

* Price
* Variation ID
* Quantity
* Shipping cost

# 37. Core Development Principle

The plugin should be a **lightweight Elementor widget for WooCommerce**, not a new WooCommerce platform.

Architecture:

```text
WordPress
    ↓
WooCommerce
    ↓
Custom Elementor Widget
    ↓
Product Selection
    ↓
Variation Selection
    ↓
Native WooCommerce Checkout
    ↓
Native WooCommerce Payment
    ↓
Native WooCommerce Order
    ↓
WooCommerce Thank You Page
```

WooCommerce remains the source of truth for:

* Product
* Variation
* Price
* Stock
* Cart
* Checkout
* Shipping
* Payment
* Order
* Thank You page

The custom plugin only provides the UI and Elementor integration.

# 38. Final Expected User Experience

The Elementor user should be able to:

1. Drag **Product Variation & Checkout** widget onto any Elementor page.
2. Keep **Current Product = ON** by default.
3. Or turn it OFF.
4. Search and select any WooCommerce product.
5. If the product is Simple:

   * Show title
   * Show image
   * Show price
   * Show quantity
   * Show checkout
6. If the product is Variable:

   * Automatically detect its attributes.
   * Select Image or Button display for each attribute.
   * Select variation options.
   * Update product image/price according to the selected variation.
7. Show/hide:

   * Title
   * Image
   * Price
   * Quantity
   * Variations
   * Checkout
8. Fully style every section using Elementor.
9. Configure responsive settings.
10. See all changes live inside the Elementor editor.
11. Customer completes the native WooCommerce checkout.
12. Customer clicks **Order Now**.
13. WooCommerce processes the order.
14. Customer is redirected to the normal WooCommerce Thank You page.

The final product should feel like a **native Elementor WooCommerce widget**, while keeping WooCommerce responsible for all actual commerce functionality.
